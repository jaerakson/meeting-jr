## PR #79 (apply-match 충돌 해소) 후속 과제

### 1. speaker mapping 구조 리팩터링 (중기)
- **현재**: transcript 내 문자열 토큰(`아빠:`)을 정규식으로 치환하는 방식. 이름 맞바꾸기·충돌 등에서 복잡도가 증가한다.
- **목표**: 각 transcript 라인이 `label` 필드를 직접 보유하여 치환이 `label → display_name` 매핑 조회로 단순화. DB 스키마 변경 필요.
- **효과**: apply-match의 3c(정규식)/3d(라인별) 분기가 불필요해지고, 이름 맞바꾸기도 자명하게 처리됨.

### 2. `_resolve_speaker_display` 정규식 위험
- `r"\[(\d{{2}}:\d{{2}})\]\s*(.+?):"` 패턴이 콜론 앞 토큰을 화자명으로 인식하는데, 콜론 뒤 공백을 요구하지 않는다.
- 발화 내용에 시간 표현(`15:00`)이 포함되면 거짓 양성이 발생할 수 있다.
- **저위험**: `[MM:SS]` 타임스탬프가 라인 시작에만 있으므로 실제 충돌 가능성은 낮다. 그러나 라벨 기반 리팩터링(위 1번)으로 근본 해결 가능.

### 3. 미해결 저위험 사항
- `new_name` 미trim: `label_to_current` 값은 `.strip()` 처리되지만, `matches` dict 값(`new_name`)에는 trim이 없다. 현재 프론트가 trim을 보내므로 실질 위험 없으나, 방어적으로 백엔드에서도 trim 추가를 권장.
- 3c/3d 텍스트 매칭 오염 가능성: 발화 내용에 화자명과 동일한 문자열이 있으면 정규식 치환(3c)이 본문까지 치환할 수 있다. `_resolve_speaker_display`와 동일 패턴(`^\[...]\s*NAME:`)으로 라인 시작 위치 한정이 필요할 수 있다.

새 회의 종속 상태가 추가될 때마다 이 열거에서 누락되기 쉬운 구조다. 아래 5건 모두 이 열거에
빠진 상태 때문에 발생한다. 재현 경로는 전부 공통이다: **어떤 모달/편집 모드를 연 채로 사이드바에서
다른 회의를 선택**하면, 화면은 새 회의를 보여주는데 그 모달/편집 상태만 이전 회의 컨텍스트로
남는다.

심각도 순(가장 심각한 것부터):

1. **`showRematchModal` + `rematchResult` — 가장 심각.** 음성 매칭 모달이 열린 채 회의를
   전환하면 이전 회의의 화자 매칭 결과로 **새 회의에 잘못된 화자 이름이 DB에 기록된다.**
   이 PR이 닫은 것과 **같은 부류의 사고이며, 경로만 다르다.** 재요약 건(4번)보다 나쁘다.
2. **`editingTitle` + `titleValue`.** 정확히는: `titleValue`는 별도의
   `useEffect(() => { if (job) setTitleValue(job.title || '') }, [job?.id, job?.title])`가
   회의 전환마다 새 회의의 제목으로 갱신하지만, **편집 모드 플래그인 `editingTitle`은 리셋되지
   않는다.** 그 결과 회의를 전환해도 제목 입력창이 열린 채로 남고(안에 표시되는 값 자체는 새
   회의의 제목으로 정상 갱신됨), 사용자가 그 상태에서 그대로 저장하면 새 회의 자신의 제목을
   다시 저장하는 정도로 그친다 — 다만 사용자가 그 사이 입력을 시작했다면 그 입력이 새 회의의
   제목으로 저장될 위험은 남는다.
3. **`showNotionConfirm`.** 확인 모달이 열린 채 남아 **엉뚱한 회의를 Notion에 내보내거나
   기존 Notion 페이지를 덮어쓸** 수 있다.
4. **`showResummarizeModal`** — 처음 발견한 건(아래 기존 내용). 재요약은 기존 요약을 덮어쓰는
   파괴적 동작이다.
5. **`editData`.** 이전 회의의 `awaiting_edit` 데이터(전사 편집용 임시 상태)가 새 회의 화면에
   남는다.

(`copied`·각종 `*Loading` 플래그는 무해해서 목록에서 제외했다.)

### 4번 상세 (처음 발견한 재현 경로 — 그대로 보존)
- **재현 경로**: 편집 진입 → 재요약 모달 오픈 → (모달을 닫지 않은 채) 사이드바에서 다른 회의로
  전환 → 그 회의 화면에서 "재요약 실행"을 누른다.
- **현재 상태**: `a4c97fb`로 이 경로의 **증상(화자 이름 소실)만** 막았다 —
  `localSpeakerMap`이 nullable이 되면서 `?? job.speakers ?? {}`가 새 회의의 `job.speakers`로
  정상 폴백하게 됐다. **잘못된 회의에 재요약이 실행되는 것 자체는 그대로 남아 있다.**
- **영향**: 재요약(`POST /api/jobs/{id}/finalize`)은 기존 요약을 덮어쓴다 — 사용자가 의도하지
  않은 회의의 요약이 조용히 재생성되는 **파괴적 동작**이다. 단순 UX 결함이 아니라 데이터
  덮어쓰기 위험이라 후속 과제 우선순위가 낮지 않다.

### `res.ok` 미검사 항목(위 섹션)과의 관계
같은 계열의 결함이다 — "실패·오상태를 사용자에게 알리지 않고 진행한다." 이쪽은 응답 실패가
아니라 **모달/편집 상태가 열린 채로 컨텍스트(job)만 바뀌는 상태 불일치**라는 점이 다르지만,
"사용자가 인지하지 못한 채 되돌릴 수 없는(또는 잘못된 대상에 대한) 서버 액션이 실행된다"는
결과는 같다.

### 제안 수정 방향 (구현하지 않음)
개별 열거 대신 회의 종속 상태를 한곳에 모아 일괄 리셋하거나, `<MainArea key={job.id} .../>`로
컴포넌트를 재마운트한다.
