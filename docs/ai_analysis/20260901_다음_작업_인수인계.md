### A. [1순위] 회의 전환 시 이전 회의 상태 잔존 — 전 5건

**성격**: 데이터 쓰기 사고. UX 결함이 아니다.
**상세 명세**: `docs/ai_analysis/20260828_잔여_기획_후보.md` 의 "★ 다음 PR 확정 안건(1순위)" 절 (160행~). **착수 전 반드시 읽을 것.**

**공통 근본 원인** (실측): `frontend/components/MainArea.tsx:89-99` 의 `[job?.id]` 이펙트가 회의 종속 상태를 **전수 리셋하지 않고 9개만 개별 열거**한다. 파일에 `useState`는 22개 있다. 열거에서 빠진 것들이 아래 5건이다.

**재현 경로 (5건 공통)**: 어떤 모달/편집 모드를 **연 채로** 사이드바에서 다른 회의를 선택 → 화면은 새 회의인데 그 모달 상태만 이전 회의 컨텍스트로 남는다.

심각도 순:
1. **`showRematchModal` + `rematchResult` — 가장 심각.** 이전 회의의 음성 매칭 결과로 **새 회의에 잘못된 화자 이름이 DB에 기록된다.** PR C가 닫은 것과 같은 부류, 경로만 다르다.
2. **`editingTitle`** — 제목 편집 플래그가 안 닫힌다. `titleValue` 자체는 별도 이펙트로 갱신되나, 전환 중 입력을 시작했다면 그 입력이 새 회의 제목으로 저장될 위험.
3. **`showNotionConfirm`** — 엉뚱한 회의를 Notion에 내보내거나 기존 페이지를 덮어쓸 수 있다.
4. **`showResummarizeModal`** — 재요약은 기존 요약을 덮어쓰는 파괴적 동작. PR C(`a4c97fb`)에서 **증상(화자 이름 소실)만** 막았고 **잘못된 회의에 재요약이 실행되는 것 자체는 그대로 남아 있다.**
5. **`editData`** — 이전 회의의 `awaiting_edit` 임시 상태가 새 회의 화면에 남는다.

**범위 축소는 배제됨**: 1번만 두 줄로 막는 안은 팀리드가 명시적으로 배제했다. 몇 개만 패치하면 열거 목록을 늘리는 것일 뿐, 다음에 상태가 추가되면 또 누락된다.

**수정 방향 2안**:
- (a) `<MainArea key={job.id} />` 로 재마운트 — **사용처가 2곳뿐**(`frontend/app/page.tsx:150`, `frontend/app/meetings/[id]/page.tsx:55`)이라 실질 2줄.
- (b) 회의 종속 상태를 한곳에 모아 일괄 리셋.

**(a)가 유력한 근거 (실측)**: `MainArea`는 `EventSource`를 직접 들고 있지 않다(SSE는 `ProgressCard` 소관). ref는 `audioPlayerRef`/`titleSavingRef` 2개뿐. `key`는 `job.id`가 바뀔 때만 재마운트하므로 같은 회의 내 `awaiting_edit` 흐름은 안 건드린다.

**견적: 작업 세션 1회(집중 3~5시간). 리뷰에서 회귀가 나오면 최대 2세션.**
- 구현은 작다. 시간을 먹는 것은 검증이다:
  - 5건 각각 재현 → 회귀 잠금 테스트 (`frontend/__tests__/MainArea.resummarize.test.tsx` 패턴 재사용 가능)
  - 재마운트가 파괴하면 안 되는 것 확인: 오디오 재생 위치, 스크롤, `relatedMeetings`/`recordingNotes` 재요청, awaiting_edit 진입 경로
- **불확실 요인**: 22개 상태의 회의종속/전역 전수 분류. `categories`(전역)처럼 명백한 것과 `currentTime`(재마운트로 자동 해결)처럼 애매한 것이 섞여 있다. 분류가 깔끔하면 (a) 1줄로 끝나고, 예외가 나오면 (b)로 가면서 반나절 늘어난다.
- **판단 필요**: 1번(rematch)은 DB에 잘못 쓰는 경로라 **프론트만 고치고 끝낼지, 서버측 방어도 넣을지** 결정해야 한다. PR C에서 `restore_segment_labels`를 "프론트 수정의 대체가 아니라 추가 방어"로 둔 것과 같은 논리. 백엔드가 붙으면 **+1세션**.

### B. [2순위] 테스트가 운영 DB를 오염시킨다 — 개발 인프라 결함

**제품 결함이 아니라 개발 인프라 결함이다.** 여러 세션에 걸쳐 미뤄졌다.

- **증상**: `cd backend && pytest tests/` 를 돌릴 때마다 `backend/meetings.db` 의 `recording_notes` 가 **+2행 누적**된다. 실측 이력: 404행(세션 58) → 510행(세션 60~61 시점).
- **원인 (확정)**: `backend/app/database.py` 의 `DB_PATH` 가 고정 경로이고, **`backend/tests/conftest.py` 가 아예 없다.** DB를 격리하는 픽스처가 없어 `test_recording_notes.py` 가 운영 DB에 직접 INSERT 한다.
- **현재 피해**: `recording_notes` 만 오염(실제 화면에 나오는 데이터). **`meetings` 테이블은 무사하다 — 운이 좋았을 뿐이다.**
- **위험**: `meetings` 를 쓰는 테스트가 하나라도 추가되는 순간 **사용자 회의 데이터가 오염된다.**
- **조치 방향**: `backend/tests/conftest.py` 신설 + `DB_PATH` 를 테스트에서 tmp 로 격리. 일부 테스트는 이미 `monkeypatch.setattr(db_module, "DB_PATH", ...)` 로 개별 격리하고 있으니 그 패턴을 전역 픽스처로 올린다.

> **그때까지의 필수 절차 — 예외 없음:**
> ```bash
> cp backend/meetings.db /tmp/meetings.db.bak      # 1) 백업
> cd backend && python3.11 -m pytest tests/ -q     # 2) 실행
> cp /tmp/meetings.db.bak backend/meetings.db      # 3) 복원
> md5 backend/meetings.db                          # 4) 원복 확인
> ```
> 기준 md5: `837db16f24128f8893409744429b37dd` (recording_notes 510행, meetings 10행)
> **서버가 떠 있는 상태에서 복원하면 서버를 재시작할 것.**
