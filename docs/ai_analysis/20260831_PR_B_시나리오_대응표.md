## 새 불변식 (director 확정)

> apply_match = **라벨 검증 → speaker_map 갱신 → 재렌더**.
> 표시 이름은 `speaker_map.get(label, label)` 로만 결정된다. 텍스트 매칭·overlap 휴리스틱은 없다.

- **라벨 검증**: `matches`의 키가 `get_segments(job_id)`가 반환하는 segment label 집합에 존재하는지로
  판정한다(QA 도출 — 기존 Bug3 "모르는 라벨→skipped"와 동일 기준으로 통일). diarization 조회는
  더 이상 apply_match에서 하지 않는다.
- **표시 이름 결정**: participation도 동일하게 `speaker_map.get(label, label)`로 축소.
  `_is_identity_mapped`/`seen_display_names`/`_resolve_speaker_display` 전부 제거.
- **identity-mapped 레거시 행의 라벨 네임스페이스**: PR A 이후 segment의 `label`은 그 자체로 유일한
  네임스페이스다(예: identity-mapped 행은 label="아빠", 비-identity 행은 label="SPEAKER_00"). 프론트가
  이미 `{label: name}` 형태로 보내므로(design doc 확인됨 — `handleApplyMatch`/`rematch`가 raw 라벨 키
  사용) diar-label("SPEAKER_00")과 transcript-label("아빠") 사이의 다리는 더 이상 필요 없다 — 애초에
  하나의 네임스페이스만 존재한다. **PR A 이전에 QA가 우려했던 "브릿지 소실" 문제는 이 사실로 해소된다.**

## 검산

- 재작성 후 함수 개수: `test_apply_match_label_model.py` 15개 + `test_participation_label_model.py` 6개
  + 기존 파일에서 **병합 표시 2건**(2, 16번)을 별도 함수로 유지했으므로 실제로는 **17 + 6 = 23개 함수**,
  단 흡수 표시 3건(5, 6, 17-중복아님/9번원본카운트유지)은 다른 함수 안의 **추가 assertion 블록**으로 존재
  — "무엇을 검증했는가" 기준으로 셀 때 **26개 시나리오 전부 대응처가 있다.**
- 파일을 2개로 나눈 이유: 원본도 이미 apply_match(collision+consistency 2파일)와 participation(1파일)로
  나뉘어 있었고, 새 모델에서는 "충돌"이라는 축이 사라져 collision/consistency 구분이 무의미해졌다.
  대신 **API 대상**(apply_match vs participation)으로 재편했다 — rename-speakers는 완전 신규라 별도 파일.
