## 1. 역할 구조

```
사용자
  └─ 팀리드 (오케스트레이터)      ← 이 세션. 코드를 직접 수정하지 않는다
       ├─ director               분석·설계·팀원 코디네이션. 코드 수정 안 함
       ├─ product-manager        기획 (사용자 승인 필요)
       ├─ backend-dev            백엔드 구현
       ├─ frontend-dev           프론트 구현
       ├─ ai-engineer            오디오·AI 파이프라인
       └─ qa-engineer            테스트 작성·검증
```

**시스템 제약**: 팀원은 다른 팀원을 소환할 수 없다. 소환은 팀리드만 가능하고, 팀원끼리는 메시지로 소통한다. 그래서 director가 "팀원이 필요하다"고 보고하면 팀리드가 소환하는 2단계를 거친다.

**팀리드가 직접 하는 일**: 상황 판단, 팀원 소환, 코드리뷰 실행, 검증, 머지, PROGRESS.md 기록, 팀 정리.

## 2. 실제 진행 흐름

### 기능 개발 (프로세스 A)
```
사용자 요청
  → 팀리드: 기획 필요 여부 판단
  → (필요 시) product-manager 기획안 → 사용자 승인   ← 유일한 사용자 개입 지점
  → director 분석 → 수정 범위·필요 팀원 보고
  → 팀리드가 팀원 소환
  → qa-engineer 테스트 선작성 → 실패 확인 (TDD 레드)
  → developer 구현 → 통과 (TDD 그린)
  → qa-engineer 재검증
  → director PR 생성 → 팀리드 보고  ← 이 시점이 코드 프리즈
  → 팀리드 코드리뷰
  → 이슈 있으면 수정 지시 → 재검증
  → 팀리드 머지 → 브랜치 정리 → PROGRESS.md 기록 → 팀 종료
```

### 버그 수정 (프로세스 B)
기획 단계를 건너뛰고 director 분석부터 시작한다. 나머지는 동일하다.

## 4. 무엇이 효과가 있었나

### 4.1 코드리뷰가 테스트를 보완했다
테스트 200개가 통과해도 리뷰가 잡은 것들:
- 트랜스크립트가 통째로 한 이름으로 합쳐지는 데이터 붕괴 (PR #79)
- 사용자가 "적용됐다"고 믿는데 실제로는 아무것도 안 바뀜 (PR #79)
- 화면에만 반영되고 저장은 안 되는 사용자 확정 (PR #76)
- PR의 핵심 기능에 사용자 진입점 자체가 없음 (PR #76)

**원인**: 테스트가 "고친 경로"만 확인하고 실제 사용자 경로를 지나지 않았다. DB를 직접 조작하거나 엔드포인트를 직접 호출하는 테스트는 프론트가 실제로 보내는 payload 형태를 검증하지 못한다.

### 4.2 재현 케이스를 테스트로 고정하는 절차
리뷰에서 나온 재현 시나리오를 반드시 테스트로 남기게 했다. 이게 회귀 방지막이 됐다. PR #78에서 고정한 3건은 PR #79 작업 중에도 계속 검증됐다.

### 4.3 팀리드의 독립 검증
팀원 보고를 그대로 믿지 않고 팀리드가 직접 diff를 읽고 테스트를 돌렸다. 이 과정에서 잡은 것:
- 보고와 달리 구현이 깨진 상태 (호출부는 인자를 넘기는데 함수 시그니처엔 없음)
- DEVGUIDE 반영 주장이 실제로는 누락
- 테스트 실패가 진짜 버그인지 인프라 오류인지 구분

### 4.4 판단 근거를 요구하는 것
director가 "이 상태는 실제로 발생하지 않는다"고 한 판단이 틀렸던 적이 있다. 그 상태를 만들어내는 코드 경로가 바로 같은 함수 안에 있었다. 이후 "발생하지 않는다"는 주장에는 근거를 요구하도록 했다.

## 5. 무엇이 문제였나

### 5.1 리뷰 비용 과다 (사용자 지적)
`/code-review:code-review` 스킬은 한 라운드에 **에이전트 13개**를 쓴다. 준비 3개 + 리뷰 5개 + 채점 5개. 라운드당 대략 70만~100만 토큰이다. PR #78~#79 구간에서만 이 사이클을 다섯 번 돌았다.

**개선**: 작은 수정과 재리뷰는 팀리드가 직접 diff·테스트로 검증한다. 전체 프로토콜은 큰 기능 PR에만 적용한다.

### 5.2 같은 부류 버그의 반복
화자 매핑 영역에서 다섯 라운드 연속 같은 부류 버그가 나왔다.
- PR #66이 폐기한 포인트 매칭이 **두 번** 재도입됐다 (PR #78, PR #79)
- 공백 불일치를 고치려던 수정이 **같은 버그의 새 변종**을 만들었다 (PR #79)
- 문서-구현 불일치가 **다섯 번 연속** 지적됐다 (PR #75~#79)

**원인**: 화자 이름을 문자열 토큰으로 다루는 구조. 같은 토큰을 쓰는 서로 다른 라벨을 구분할 수 없고, 타임스탬프 판별 로직을 매번 새로 짜다 보니 폐기된 방식이 반복 유입된다.

**결론**: 패치 반복으로 끝나지 않는다. 후속 과제로 "화자 매핑을 라벨 기준으로 다루는 리팩터링"을 기록했다.

### 5.3 중단 사고
- 사용자가 창을 닫아 팀 6개가 동작 불능이 됐다. 작업물이 미커밋 상태여서 유실 위험이 있었다.
- 계정 세션 한도로 팀 전체가 중단됐다. 중간 상태가 깨진 채로(호출부와 시그니처 불일치) 남아 있었다.

**개선**: 작업 단위마다 즉시 커밋한다. 중단 시 팀리드가 WIP 커밋으로 보호한 뒤 새 팀을 구성한다.

### 5.4 리뷰 중 코드가 움직임
PR #78 리뷰 도중 커밋 2개가 추가돼 리뷰 대상 SHA가 바뀌었다. 리뷰를 처음부터 다시 돌려야 했다.

**개선**: "PR 생성 보고 = 코드 프리즈"를 규칙으로 정착시켰다. 이후 리뷰 결과를 받고 나서만 추가 커밋한다.

### 5.5 팀원이 테스트에 맞춰 구현을 끼워맞춤
실패하는 테스트를 만나자 구현을 고쳐서 통과시키려 한 적이 있다. 그런데 그 테스트는 **낡은 것**이었고(PR #67이 의도적으로 바꾼 UX를 반영 못 함), 구현이 옳았다. 자칫 사용자가 승인한 UX 결정을 되돌릴 뻔했다.

**개선**: 실패 테스트를 만나면 `git log`로 **테스트와 구현 중 어느 쪽이 나중에 바뀌었는지** 먼저 확인한다. 구현 회귀면 구현을, 의도적 변경에 테스트가 안 따라온 것이면 테스트를 고친다.

## 6. 정착된 운영 규칙

### 커밋·브랜치
1. 작업 단위마다 즉시 커밋한다. 완성될 때까지 미루지 않는다.
2. `feature/<기능명>` 또는 `fix/<버그명>` 브랜치. main 직접 커밋 금지.
3. 머지는 `--squash --delete-branch`. 이후 로컬 브랜치 전체 정리(main 제외) + `git remote prune origin`.

### 리뷰
4. **PR 생성 보고 시점 = 코드 프리즈.** 리뷰 결과 전까지 추가 푸시 금지.
5. 코드리뷰 없이 머지 금지. 다만 규모에 따라 강도를 조절한다.
6. 리뷰에서 나온 재현 케이스는 반드시 테스트로 고정한다.

### 테스트
7. TDD 순서 준수: 테스트 선작성 → **실패 확인** → 구현 → 재검증.
8. UI가 개입하는 기능은 다음을 반드시 포함한다.
   - 프론트가 **실제로 보내는 payload 형태**로 API를 호출하는 테스트
   - 사용자가 화면에서 밟는 **경로 전체**를 재현하는 테스트
   - 새 필드가 **NULL인 기존 데이터**에서 정상 동작하는지
9. 데이터 정합성 코드는 세 축을 점검한다: **여러 값이 하나로 수렴하는 경우 / 부분 적용 / 데이터 소스가 아예 없는 경우.**

### 문서
10. 확정 결정사항은 DEVGUIDE.md 섹션 10에, 신규 API는 섹션 6에 기록한다.
11. **"안 되는 것"(한계)을 반드시 함께 적는다.** 되는 것만 적어서 생긴 오해가 반복됐다.
12. 문서를 쓸 때 코드와 한 줄씩 대조한다.

### 검증
13. 팀리드는 팀원 보고를 그대로 믿지 않고 직접 diff를 읽고 테스트를 실행한다.
14. "이 상태는 발생하지 않는다"는 판단에는 그 상태를 만드는 코드 경로가 없다는 근거를 요구한다.
15. 테스트 실패 시 실패 원인이 진짜 버그인지 인프라 오류인지 구분한다.

### 사용자 개입
16. 기획안 승인이 유일한 필수 개입 지점이다. 그 외에는 확인 질문 없이 판단하고 실행한 뒤 결과를 보고한다.
17. 설계 방향이 크게 바뀌거나 승인 범위를 넘는 변경은 사용자에게 먼저 알린다.
