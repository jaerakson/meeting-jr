## 왜 패치가 아니라 설계 변경인가

이 영역에서 **5라운드 연속 같은 부류 버그**가 나왔다 (PR #78 3건 → PR #78 재리뷰 4건 → PR #79 4건).
운영 규칙: "같은 부류 이슈가 3회 이상 반복되면 패치를 멈추고 설계 안건으로 전환한다."

**근본 원인 한 줄: `finalize_job` (main.py:396-401).**
speaker_map이 identity면 transcript에서 이름을 재파싱해 **speaker_map 키를 라벨→이름으로 갈아끼운다.**
라벨 정체성이 여기서 파괴되고, 하위의 모든 코드는 그것을 되짚는 추측이다.
DEVGUIDE §10의 다섯 "확정 결정사항"이 전부 이 손실의 보상 장치다.

### 실측된 구조적 부채
- 같은 문법을 파싱하는 **정규식 11개가 서로 다른 방언**으로 흩어져 있다 (백엔드 7 / 프론트 4). 공유 모듈 없음.
- 같은 overlap 휴리스틱이 **4벌 중복 구현**: `_resolve_speaker_display`(2294) / apply_match 3d(1926-1937) /
  participation 폴백(2424-2440) / `save_speaker_profile`(2546-2580).
  호출부마다 판별 로직을 새로 짜는 구조라 **PR #66이 폐기한 포인트 매칭이 두 번 재유입**됐다.
- 나이브 `.replace(speaker_id, name)` 2곳 생존: finalize:411-414, regenerate_summary:521-524.
  3c가 방어하는 본문 오염을 여기선 그대로 맞는다.

### 부수적으로 발견된 미보고 결함 2건 (코드 확인, 추정 아님)
1. `rename-speakers`(main.py:2084)는 `speakers`만 쓰고 transcript를 건드리지 않는다 → **구조적 desync가 보장**된다.
   `SpeakerMapper.tsx:50`에서 실제 호출되는데 **백엔드 테스트 0건**.
2. `TranscriptEditor.tsx:25`가 화자를 `\S+`로 잡아 **공백 포함 실명("김 팀장")이 재편집 시 파싱 실패**.
   다른 3개 파서는 `.+?`라 통과 — 방언 불일치가 만든 실버그.
3. 타임스탬프 자릿수: 생산자는 `{minutes:02d}`(무제한)인데 finalize는 `\d{2}`(정확히 2자리)
   → **100분 초과 회의에서 이미 불일치.**

## 확정 설계

### 저장 표현
**`transcript_segments TEXT` (JSON `[{start,end,label,text}]`) 신설. 문자열 `transcript`는 파생값으로 유지.**
완전 교체하지 않는다.

근거 — 전수조사 결과 문자열 소비자가 깨끗이 두 부류로 갈린다:

| 부류 | 위치 | 처리 |
|------|------|------|
| **구조 파싱**(라벨 필요) | apply_match 3c·3d(1888-1943), `_resolve_speaker_display`(2294), participation 폴백(2424-2440), `save_speaker_profile` 폴백(2546-2580), finalize 재파싱(397), 프론트 4곳 | 이번 전환/삭제 대상 |
| **문자열 통과**(구조 불필요) | ask(759), share·shared(787-810), ZIP export(1561-1566), followup(2253), summarizer 프롬프트, `search_jobs`의 SQL `transcript LIKE ?`(database.py:419) | 손대지 않음 |

즉 **버그는 전부 *변경* 경로에 있고 *읽기* 경로엔 없다.** 문자열을 없애면 얻는 것 없이
13/25 테스트파일과 검색 SQL을 깨뜨린다.

transcript를 아예 쓰지 않는 곳(확인): insights, action-items, notion_sync, related-meetings, print/PDF(의도적 제외, print page:156).

### 강제 불변식
> **transcript 문자열은 다시는 in-place 변경하지 않는다. 오직 `render(segments, speaker_map)` 출력으로만 쓴다.**

Writer가 4곳뿐이고(main.py:288 txt업로드 / 403 finalize / 649 PATCH transcript / 1958 apply_match)
전부 `update_job_result`(database.py:272) 관문을 지나므로 강제 가능하다.

### 하위 호환
**lazy 파싱 + 조회 시 백필.** 일괄 마이그레이션하지 않는다.
이 코드베이스에 이미 검증된 동일 패턴이 있다 — diarization의 DB→파일 폴백 + `update_job_result` 백필(main.py:2364-2367).
스키마 변경은 기존 `_migrate()`의 additive ALTER 목록(database.py:92-110)에 한 줄 추가로 끝난다.

### segments 생산 지점 2곳 (둘 다 새 정보 불필요)
- `merge_and_save`(audio_processor.py:465) — diarization 경로, 라벨을 이미 정확히 보유
- `_parse_txt_transcript`(main.py:1585) — txt·ClovaNote 경로, 원본이름→SPEAKER_XX 맵을 이미 만든다(1645)

  `applied_labels`, 3c 정규식 치환, 3d 라인별 overlap 매칭

- `save_speaker_profile` 폴백 휴리스틱(2546-2580)

`rename-speakers`(2084)에 재렌더를 붙여 desync 해소.
**프론트 계약 변경 없음** — `handleApplyMatch`(MainArea.tsx:341-351)가 이미 `{label: name}`을 보내고

### PR C — finalize·프론트 라벨 왕복
- `finalize_job`의 identity 재키잉(396-401)과 나이브 `.replace`(411-414) 삭제. `regenerate_summary`(521-524) 동일.
- TranscriptEditor가 segments(라인별 label 보존)로 왕복.
- 프론트 파서 4개 + 시리얼라이저 2개를 **공유 모듈 1개로 통합** → `\S+` 공백 이름 버그 동시 해소.
- body에 segments가 없으면 기존 문자열 경로로 폴백(구버전 번들 방어).

## 회귀 위험 (가능성 순) 과 대응 테스트

1. **[최대] 기존 행의 lazy 파싱 무손실성** — 현재 모든 회의가 segments NULL.
   ClovaNote 유래 병합 텍스트, 이름에 `:`/`[` 포함, 빈·깨진 transcript에서 파싱이 깨지면 **조용히 오염**된다.
   → 실데이터 형태 코퍼스로 왕복 테스트 + 백필 후 **문자열 바이트 동일성** 단언.
2. **identity-mapped 레거시 행** — speaker_map 키가 라벨이 아니라 실명인 기존 행.
   파싱 시 label=이름이 되어 매핑이 identity로 안정된다(렌더가 동일 문자열을 낸다).
   단 PR B가 여기서 깨질 수 있어 **명시적 테스트 필수**.
3. **파생 문자열 드리프트** — segments 갱신 없이 transcript만 쓰는 코드가 남으면 조용히 desync.
   → 변경 엔드포인트마다 `render(segments, speaker_map) == job.transcript` 사후 단언.
4. **타임스탬프 자릿수** — 위 결함 3. PR A 파서에서 고정.
